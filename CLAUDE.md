# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

An AstrBot plugin that acts as a single-user Vikunja todo secretary, accessible via QQ official bot private chat and WeChat (`weixin_oc`) private chat. Both entry points share the same Vikunja workspace. The plugin provides slash commands (`/todo`) and registers six LLM Tools so models with tool-calling enabled can manage tasks through natural language conversation.

**License:** AGPL v3

## Commands

```bash
# Run all tests
python -m unittest discover -s tests -v

# Run a single test file
python -m unittest tests/test_domain.py -v
```

No build or lint steps are configured. The only runtime dependency is `aiohttp>=3.9,<4`, listed in `requirements.txt`.

Run tests from the repo root. `tests/` import `todo_domain`, `vikunja`, `state_store`, `tool_schema`, and `push_channels` as **top-level** modules, so those five files must stay at the repo root even though `main.py` imports them relatively as a package (`from .todo_domain import ...`). That top-level constraint is why `push_channels.py` takes its send function as an injected callable instead of importing `astrbot.api` — the module has to be importable without AstrBot installed.

A syntax gate that works **without** `astrbot` installed (`py_compile` never imports): `python -m py_compile main.py tool_schema.py todo_domain.py vikunja.py state_store.py push_channels.py`.

## Packaging

`metadata.yaml` is the AstrBot plugin manifest and the **only** place the version lives (`version`, `astrbot_version: ">=4.22.1,<5"`, `support_platforms`); bump it there when releasing. `plugin.json` is the plugin-market listing metadata (display name, desc, tags, category) and carries no version field — don't go looking for a second one to keep in sync. Neither file is read at runtime. Deployment is copying the directory into AstrBot's `data/plugins/astrbot_plugin_vikunja` and installing `requirements.txt`. The natural-language path requires a model with Tool Calling enabled; without it, slash commands still work.

## Architecture

The plugin follows a layered architecture with clear separation between the AstrBot framework integration, Vikunja API access, and pure domain logic.

### `main.py` — Plugin entry point

`VikunjaPlugin` extends `Star` (the AstrBot plugin base class). It wires together three concerns:

1. **Slash commands** via `@filter.command_group("todo", alias={"待办"})` — `/todo help`, `/todo projects`, `/todo add`, `/todo edit`, `/todo done`, `/todo reopen`, `/todo search`, `/todo subtask`, `/todo bulk`, `/todo project`, `/todo move`, `/todo label`, `/todo week`, `/todo today`, `/todo list`, `/todo remind`, `/todo push`. Every subcommand also has Chinese aliases (e.g. `add`/`添加`/`新建`). The whole group is gated by `@filter.event_message_type(filter.EventMessageType.PRIVATE_MESSAGE)`. Command bodies are generators that `yield event.plain_result(...)` and catch `ValueError`/`VikunjaError`/`PrivateOnlyError` into user-facing text — they never raise out to the framework.

   **Handler order is load-bearing**: `PrivateOnlyError` subclasses `ValueError`, so an `except ValueError:` branch placed first silently swallows it and the user sees a usage hint instead of "only private chat". Where a command needs both, catch `PrivateOnlyError` *before* `ValueError` (see `todo_done`).

   **`/todo project` does not shadow `/todo projects`.** `CommandFilter.filter()` matches with `message_str.startswith(f"{full_cmd} ")` or exact equality, so the trailing space is what separates the two. A subcommand named `projects` under the `project` group *would* collide; a sibling command does not.

2. **LLM Tool registration** via `@filter.llm_tool(name="vikunja_*")` — seven tools: `vikunja_list_projects`, `vikunja_create_task`, `vikunja_update_task`, `vikunja_delete_task`, `vikunja_manage_project`, `vikunja_list_tasks`, `vikunja_stats`. Tool docstrings serve as the LLM function descriptions. `vikunja_update_task` is the single generic write path for *existing* tasks (edit any field, move project, complete, reopen, add a subtask via `parent_id`, bulk via comma-joined `task_ids`) — it absorbed the former `vikunja_complete_task`, whose job is now `done="完成"`. Bulk is deliberately *not* a separate tool or a separate code path: `/todo bulk`, the LLM tool's `task_ids`, and `/todo edit` all funnel through `_apply_edits()`, because a second implementation is how "resolve the project selector" or "persist the reminder threshold" quietly goes missing from one of them. `SECRETARY_PROMPT` names tools explicitly, so renaming one means updating the prompt; `tests/test_tool_schema.py` parses the prompt and fails on a name that isn't registered.

3. **Background reminder loop** started in `on_astrbot_loaded()` — polls Vikunja for tasks nearing their due date and pushes notifications to registered private-chat channels (skipped entirely when `vikunja_url` or `api_token` is unset).

The reminder pipeline spans `main.py` and `state_store.py` and has several non-obvious behaviors:

- Each task's threshold is a per-task override (set by `--remind 30m` or the LLM tool) falling back to the global config value. The polling loop reads them in one shot via `state.task_reminder_overrides()`, which returns a `{task_id: minutes}` snapshot with `int` keys — the stored keys are strings and non-numeric ones are skipped, so don't reintroduce a per-task lookup in the hot loop. A task notifies when `due <= now + threshold`; already-overdue tasks always qualify.
- Delivery goes through the **pluggable channel** abstraction in `push_channels.py` rather than calling `context.send_message` directly. `_enabled_push_channels()` builds the channel objects from `build_channels(state.channels(), self._send_text, enabled_kinds=self.config.get("push_channels"))` and filters by `is_enabled()`; `_dispatch_reminders` loops over them. `AstrBotChannel.name` is the target `umo`, which is what keeps the pre-existing dedup-key format and the failure-counter keys unchanged — this refactor was deliberately behavior-preserving. `send()` returns `is not False` rather than a truthiness check because the AstrBot adapter returns `None` on success; treating falsy-as-failure would break every send.
- `push_channels.normalize_kinds()` encodes an asymmetry that is easy to get backwards: **`None` (key absent) means "use the default set"; `[]` means "explicitly nothing" = global mute.** AstrBot's `check_config_integrity()` refills a schema default only `if key not in conf` or the value `is None`, so an empty list survives verbatim and is a genuine user choice. Collapsing the two would turn "I muted everything" into "I want the default channel".
- The dedup key is `"{channel_umo}|{task_id}|{due_date}"`, marked via `mark_sent` **on both success and failure paths**. A failed send is therefore never retried, while changing a task's due date re-arms the reminder under a new key. A multi-channel task is only added to the `notified` set once *every* enabled channel has received it — passing just "some channel succeeded" would let one slow channel pin the adaptive poll cadence.
- Three consecutive send failures auto-disable that channel's reminders; the counter lives in the in-memory `_channel_failures` dict and resets on a successful send. `/todo push test` deliberately bypasses both the dedup keys and this counter — it is a connectivity probe, and writing either would let a test message mute a real channel or swallow a real reminder.
- **Polling cadence is adaptive**, not fixed. `_dispatch_reminders()` *returns* the number of seconds to sleep (this is its contract — every early-return branch must return a value). The failure mode is silent, not loud: `asyncio.wait_for(event.wait(), timeout=None)` waits **forever**, so a `None` return parks the reminder loop indefinitely with no error and no log. The delay comes from the pure function `todo_domain.next_poll_delay()`: it takes the earliest `due - threshold` across all tasks and sleeps until that moment, bounded to `[poll_interval_seconds, idle_poll_interval_seconds]`. When nothing is pending it sleeps the full idle interval instead of pinging every minute. Its `notified` argument is load-bearing: `_dispatch_reminders` passes the IDs of tasks every enabled channel has already received, because an *overdue* task always counts as "due now" — without that filter a single leftover overdue task would pin the loop back to `poll_interval` forever and quietly undo the whole optimization. The callback is computed *after* the send loop, so it reflects sends that just succeeded.
- `_reminder_loop()` waits on `self._wake` (an `asyncio.Event`) via `asyncio.wait_for`, so `_create()` can wake it immediately after creating a task. The event is cleared *before* dispatching, so a wake triggered during dispatch is never lost. Every other mutation that can move a task's reminder moment wakes it too — the channel set changing (`_register_channel` on a new channel), `/todo remind on`, and any edit or reopen (`_apply_edit`, `todo_reopen`) because a changed due date moves both the threshold moment and the dedup key. If you add another mutation that should re-arm the schedule, set `_wake` there too; the loop has no other way to learn about it.
- `_cached_projects()` memoizes the project list for `project_cache_ttl_seconds` and is used **only** by the reminder display path; `_resolve_project()` (creates and queries) always reads live data.

A `SECRETARY_PROMPT` constant is *appended* to the existing system prompt in `on_llm_request()`, for allowed senders in private chat only. It is the rule half of the "rules + tool guards" pattern; the examples and rules are written in Chinese because the bot speaks Chinese.

**LLM 工具 docstring 的硬约束（踩过一次的坑）**：`@filter.llm_tool` 的 docstring 描述**必须只占一行**。AstrBot 用 `docstring_parser.parse()`（默认 AUTO 风格）解析后遍历 `docstring.params` 生成参数 schema；解析结果为空时**会静默注册成无参数工具**——调用方传来的参数被全部丢弃，工具只能拿到空参数，且**没有任何告警**（上游 `astrbot/core/star/register/star_handler.py` 里 `for arg in docstring.params` 之后没有"签名有参数却解析出 0 个"的校验）。

描述一旦跨行，整个 `Args:` 段都会解析失败。`vikunja_create_task` 曾因为描述多写了一行，当时仅有的几个参数**全部**失效、自然语言创建待办从未成功过（斜杠命令走另一条路径，所以看起来是好的）。两条规则：

- 摘要单行 → 空行 → `Args:` → 每个参数一行 `名称(类型): 描述`；
- **无参数的工具不要写 `Args:` 段**（悬空段同样可疑）。

`tool_schema.py` 的 `tool_schema_warnings()` 是这条约束的校验器：`_check_tool_schemas()` 在 `on_astrbot_loaded()` 里扫 `vikunja_` 前缀的方法并在启动时 `logger.warning`，`tests/test_tool_schema.py` 用 `ast` 解析 `main.py` 源码（**不 import**）做同一套断言。新增工具时若 docstring 写错，测试会直接失败。

**Private-chat enforcement** is layered: the command group uses `PRIVATE_MESSAGE` filter, and `_assert_private()` checks `event.get_group_id()` plus platform and sender whitelist. This second check exists because LLM Tools are *not* covered by the command filter, so `_register_channel()` re-checks on every tool call. QQ senders are checked against `allowed_qq_sender_ids`; WeChat (`weixin_oc`) is always allowed. An empty whitelist means QQ is unchecked too — the whitelist is opt-in, not default-deny.

### `todo_domain.py` — Pure domain logic

Framework-independent module (no AstrBot imports). Contains:

- **Time parsing** (`parse_datetime`): Handles Chinese natural-language date/time expressions ("明天18点", "2小时后", "周日 20:00", ISO formats). A day or weekday with no clock time resolves to **end of day (23:59)**, not midnight — this is why the reminder guard insists on an explicit clock time. All functions take an injectable `now` for deterministic tests.
- **Repeat rule parsing** (`parse_repeat`): Maps daily/weekly/monthly, `2d`/`12h`, `每3天`/`每隔2周` and `完成后2d` to Vikunja `repeat_after` (seconds) / `repeat_mode`. The returned pair is `(0, 0)` for "no repeat" and `(0, 1)` for monthly — that zero interval is *not* "unset": `isRepeating()` is `RepeatAfter > 0 || RepeatMode == 1`, and mode 1 ignores `repeat_after` on the server. **`repeat_mode` is the whole expressive range: `0` = after `repeat_after` from the due date, `1` = monthly same-day, `2` = from the completion date.** "每周一/三/五", `工作日`, and `每 N 个月` therefore have no representation and are **rejected with an actionable alternative, never approximated** — a rounded-off interval drifts silently, and "the repeating task just doesn't appear on the right day" is close to undetectable. The refusal patterns run *before* the parseable forms so a weekday rule gets the specific explanation rather than the generic usage hint, and the cap check mirrors the server's `MaxTaskRepeatAfterSeconds` (ten years).
- **Completion window** (`completed_tasks_since`, `format_weekly_report`): The client-side half of `/todo week`. `completed_tasks_since` is a **defensive second filter** on top of the server's `done_at > now-Nd`: `done_at` is a non-pointer Go `time.Time`, so an unset value serializes as `0001-01-01T00:00:00Z`, which compares as "before anything" and would pollute any sort or "most recent" pick. `from_vikunja_time` already collapses zero-value and null to `None`, which is the judgement used here. `format_weekly_report` is pure and takes `project_paths` plus an injected `now`; it groups by project path and only emits the "busiest day" line when the window spans more than one day.
- **Command argument parsing** (`parse_add_arguments`): Uses `shlex` to tokenize `/todo add` arguments with `--due`, `--project`, `--priority`, `--repeat`, `--remind`, `--desc` flags. `--repeat` and `--remind` both require `--due`, and `parse_duration_minutes` parses the `--remind` value (`30m`/`2h`/`1d`).
- **Edit parsing** (`parse_edit_arguments` → `EditSpec`): the mirror of `parse_add_arguments` for `/todo edit <id> …`, with one crucial difference — **empty values are meaningful**. `EditSpec.payload` is already the Vikunja field-change dict, and *key presence* is the tri-state: absent = don't touch, present with `None` = clear. "Keep the old value" and "write a zero" must produce different request bodies, so never collapse the two into one sentinel. Clearing is spelled either as an empty value (`--due ""`, `--desc ""`) or as a word from `CLEAR_WORDS` (`清空`/`取消`/`clear`…), shared with the LLM tools via `is_clear_request()` — note the empty string is *not* a clear request, it means "don't change". `is_empty()` covers the case where the only change is a reminder threshold (empty payload, non-empty request). `project_selector`, the reminder threshold, and `label_change` live **outside** `payload` because none of the three is a task field: the selector needs resolving to a `project_id` by the caller (which needs the live project list), and labels travel on their own route. `is_empty()` accounts for all three, or a labels-only edit would be discarded as a no-op.
- **`parse_tristate_bool`**: `done` is shared by "complete" and "reopen", so the LLM-facing parameter is a **string** (`完成`/`撤销完成`, empty = not mentioned) rather than a `bool`. A `bool` default of `False` would read as "reopen" whenever the model edited some unrelated field of an already-finished task, silently un-completing it.
- **Secretary guard** (`secretary_clarification_reason`): Returns a clarification reason string when LLM-requested task creation is missing required information (no specific due time for reminders, work-related task without project, long-term task without deadline/repeat, etc.). Returns `None` when the request is clear enough to create. It is a **keyword heuristic**: it substring-matches `WORK_WORDS`/`LONG_TERM_WORDS` against the casefolded title, so introducing a new work or long-term domain means extending those sets in `todo_domain.py` — otherwise the guard silently stops asking for clarification.
- **Project resolution** (`resolve_project`, `build_project_paths`): Resolves project selectors (ID, unique name, or path like `fudan-work/SMX/paper`) against the Vikunja project list. `build_project_paths` constructs `parent/child` paths from `parent_project_id` relationships.
- **Task filtering and formatting** (`select_tasks`, `format_task_list`): Scope-based filtering (today/week/overdue/all) with priority-descending, due-date-ascending sort.
- **Reminder scheduling** (`next_poll_delay`): Given the task list, a default threshold, per-task overrides and the two interval bounds, returns how long the reminder loop should sleep. Pure and time-injectable, so the adaptive cadence is unit-testable without AstrBot. Thresholds are **per task** (`overrides.get(task_id, default_minutes)`) — a global value would give the wrong wake-up time.
- **`AddSpec` dataclass**: Value object representing a task creation request with a `payload()` method that produces the Vikunja API dict.
- **Bulk/subtask/project/move parsing**: `parse_task_ids` (`12,15,#20` — order-preserving, de-duplicating, raising on a non-numeric token) backs `parse_bulk_arguments` → `BulkSpec`, and also the LLM tools' `task_ids` string. `parse_subtask_arguments` → `SubtaskSpec` (the child may be given as an ID *or* as a title, so `SubtaskSpec` carries both `title` and `child_id`), `parse_project_arguments` → `ProjectSpec`, `parse_move_arguments` → `(task_id, project_selector)`. All of them raise `ValueError` with Chinese usage text; the command bodies turn that into chat output.
- **Search filtering** (`filter_tasks_by_query`): case-insensitive substring match over **title or description**, client-side. Deliberately not the server's `GET /tasks?s=`: the docs say "match tasks by their title" but the implementation is a PostgreSQL full-text search over title *and* description, so its behavior differs by version and database backend. Client-side is the same everywhere and can match descriptions, which the doc'd contract wouldn't have allowed.
- **Task relations** (`related_tasks_of`, `subtasks_of`, `parents_of`): subtasks are a **relation**, not a field — there is no `parent_id` on the Task struct. Vikunja exposes them under `related_tasks.subtask` / `related_tasks.parenttask` on a plain `GET /tasks/{id}`, so reading a task's children needs no extra request. `format_subtask_list` renders them.
- **Labels** (`parse_label_changes`, `build_label_index`, `filter_tasks_by_label`, `LabelChange`/`LabelSpec`): `+`/`-` prefixes give incremental add/remove; a bare list is an **overall replacement**; `""` clears. `merge_label_changes` makes repeated `--label` flags accumulate rather than let the last one win. `build_label_index` keys on `label_cache_key` (strip + casefold) and resolves duplicate titles **by comparing IDs** — the `labels` table has no unique constraint on `title`, so with `setdefault` the winner would depend on whatever order the server returned.
- **Sender authorization** (`platform_sender_is_allowed`): `weixin_oc` always passes; QQ platforms check the whitelist.

### `vikunja.py` — Vikunja API client

Async HTTP client wrapping the Vikunja v2.3 REST API using `aiohttp`:

- `normalize_api_url()`: Ensures the configured URL ends with `/api/v1`.
- `VikunjaClient`: Lazy-initializes an `aiohttp.ClientSession` with Bearer token auth. Methods: `list_projects`, `get_project`, `create_project`, `merge_update_project`, `create_task`, `get_task`, `update_task`, `merge_update_task`, `delete_task`, `complete_task`, `reopen_task`, `list_tasks`, `add_relation`, `remove_relation`. `_paged_get()` is the shared pagination loop (all three list methods use it) and follows `x-pagination-total-pages`, with "server returned an empty page" as a second termination condition. **Paging is not optional**: `per_page`'s ceiling is the server's `maxitemsperpage` (default 50) and is clamped *only in the web handler*, so an oversized value is silently reduced rather than rejected — a single-page request is silent data loss. Params are passed as a **list of tuples, not a dict**, because `list_tasks` sends `sort_by`/`order_by` twice and a dict would keep only the last. `list_projects` drops archived projects after paging.
- **`POST /tasks/{id}` treats the body as the task's new *state*, not a patch, and the resulting semantics for omitted fields are a *mix*.** `UpdateWeb` binds the body to `EmptyStruct()` — a brand-new empty `Task`, never the stored one — then `Task.Update()` → `updateSingleTask(s, a, nil)` does three things in order:
  1. The "preserve omitted fields by name" block (`t.Title = ot.Title`, …) is guarded by `if len(fields) > 0`; `fields == nil` means **it is skipped entirely**.
  2. `mergo.Merge(&ot, t, mergo.WithOverride)`: mergo ignores zero values, so anything left empty in the body **does not** overwrite the stored value. An omitted `title` therefore survives.
  3. An explicit zeroing block immediately overturns mergo for a specific list: `done`, `priority`, `description`, `due_date`, `start_date`, `end_date`, `hex_color`, `percent_done`, `repeat_after`, `repeat_mode`, `is_favorite` are all **cleared when omitted**.
  The user's empirical result (a bare `{"done": true}` kept the title) is mergo's doing, not evidence of a full replace — and that same test did *not* check the due date, description, priority or favorite flag, all of which were being cleared. Verified in the local `main` checkout (v2.6.0-521); the `if len(fields) > 0` block is an *additional* guard for the v2 per-field path, not a replacement for this one, so it is not a version difference.
- **`xorm:"-"` fields carry unconditional side effects** and are the reason a "writable columns" whitelist is unsafe. None of these are columns, so none appears in any writable-field list — yet **omitting them clears them**:
  - `ot.updateReminders(s, t)` deletes every `TaskReminder` for the task and rebuilds from the body, **with no nil guard** ⇒ omitting `reminders` wipes the native reminders set in the web UI.
  - `ot.updateTaskAssignees(s, t.Assignees, a)` runs in the same unconditional prologue and issues a plain `DELETE FROM task_assignees` when the slice is empty ⇒ omitting `assignees` wipes every assignment.
  - `is_favorite` is diffed against the stored state (absent ⇒ falsy ⇒ `removeFromFavorite`) ⇒ omitting it un-favorites the task.
  - `labels` is the exception: the update-path handler for it is commented out upstream, so echoing labels is harmless redundancy.
  A whitelist-based merge silently did all three destructive things on every title edit; that was a real data-loss bug, not a formatting nit. Note the frontend's own `writableFields` list (`frontend/src/client/queries/taskMutations.ts`) is **narrower** than what is safe here — it omits `assignees` — so do not "align" the echo set to it.
- **The hard rule: never send a partial body — echo back the object you read.** `merge_update_task(task_id, changes)` is the only safe write path, and it does what Vikunja's own web UI does: seed the payload from the **entire GET response** minus `TASK_ECHO_EXCLUSIONS`, `setdefault` every `TASK_WRITABLE_FIELDS` key (fixed shape, so a sparse GET can't degrade into a partial write), overlay `changes`, refuse an empty title, then POST. `TASK_ECHO_EXCLUSIONS` holds server-managed fields (`id`/`created`/`updated`/`created_by`/`index`/`position`) plus `project_id` — omitted unless the caller passes one, because absent means "don't move" and echoing back a just-read value would undo a concurrent move made in the web UI. Pass `current` to reuse a task you already fetched. `tests/test_vikunja.py::MergeUpdateTaskTests` asserts the emitted body (including that the side-effect fields survive and the exclusions don't), so a regression to pass-through `changes` fails loudly.
- A value of `None` in `changes` means **clear this field** — those keys must be sent, not skipped. For the server "key absent" and "key null" are equivalent; only the client-side merge distinguishes them (absent = keep, null = clear).
- **Projects use a whitelist echo, not the task-style "whole object minus exclusions"** — the two are deliberately different. `UpdateProject` reads a closed set of fields (`colsToUpdate` = `title`/`is_archived`/`identifier`/`hex_color`/`position`, plus `description` only when non-empty and `parent_project_id` only when the pointer is non-nil), so `PROJECT_ECHO_FIELDS` can enumerate the complete set. Echoing the *whole* project would instead ship `views` (a nested list) and `owner` (an object) back to the server. `parent_project_id` being a pointer is why omitting it leaves the parent alone while an explicit `0` detaches to top level; `merge_update_project` drops `None`-valued changes entirely (unlike tasks, where `None` means clear) and never sends an empty description.
- `create_project` uses **`PUT /projects`** — v1 creates with PUT and updates with POST, the reverse of the task routes. `merge_update_task`'s sibling `merge_update_project` is the same read-merge-write shape for the same reason: a bare `{"title": ...}` would clear the other columns.
- `add_relation(task_id, other_task_id, "subtask")` → `PUT /tasks/{id}/relations`; the **parent is in the URL path and the child is `other_task_id`**, which is easy to get backwards. The server creates the inverse `parenttask` relation itself — never send it too. Removing is `DELETE /tasks/{id}/relations/{kind}/{other}`, and it must be issued against the **parent's** id, which is why detaching a subtask requires reading the child and walking its `parenttask` list first.
- `complete_task()` / `reopen_task()` are `merge_update_task` with `{"done": True/False}` — Vikunja has no dedicated complete endpoint. On a **repeating** task Vikunja advances the due date rather than finishing it and returns `done: false`; `todo_done` and `vikunja_update_task` detect this and report "重复规则已推进到下一周期" instead of claiming completion. Don't assume `done == True` after a successful call.
- `list_tasks()` filters server-side with `done = false` and an optional `project_id`, so returned tasks are always unfinished. **`done` is not a query parameter** on `GET /tasks` — `TaskCollection` has no such field and there is no `query:"done"` tag repo-wide, so passing it is silently ignored; the `done = false` here is the *filter* expression, which is the mechanism that actually works.
- `list_completed_since(days)` filters with `done = true && done_at > now-Nd` and sorts `done_at desc`. `done_at` is a real indexed column and the relative-time filter is taken verbatim from Vikunja's own filter test suite, so this is server-side. Deliberately **not `updated`**: editing a title or adding a label refreshes `updated`, which would pull last month's finished work into this week's report. Its output still needs `todo_domain.completed_tasks_since` to drop zero-`done_at` rows.
- **Label methods** (`list_labels`, `create_label`, `add_task_label`, `remove_task_label`, `set_task_labels`) are a separate route group from the task-field update path — labels never travel in a task body. `add_task_label` sends `{"label_id": N}` (**an ID, not a title**) and the server raises `ErrLabelIsAlreadyOnTask` if it is already attached, so callers must diff against the task's current labels first; that is why `_apply_label_change` reads the task even on the add path. `set_task_labels` uses `/labels/bulk`, whose semantics are "this list is the complete set". Both `GET /tasks` and `GET /tasks/{id}` populate each task's `labels`, which is what makes the pre-add diff and the client-side label filter work without extra requests.
- `VikunjaError`: User-presentable exception wrapping HTTP errors and connection failures.

Gracefully handles missing `aiohttp` at import time (`aiohttp = None` fallback) so schema/unit tests can import the module without the dependency installed.

### `state_store.py` — Persistent state

Wraps AstrBot's per-plugin KV storage (`get_kv_data`/`put_kv_data` under the single key `state_v2`) with an in-memory cache and async locking. State is **not** loaded at construction time — `await state.initialize()` must run first, which `VikunjaPlugin._ensure_ready()` does lazily (double-checked under `_ready_lock`) from `_register_channel()`. Stores three namespaces:

- `channels`: Registered private-chat channels (QQ/WeChat) with per-channel `reminders_enabled` flag.
- `task_reminder_minutes`: Per-task custom reminder thresholds. `set_task_reminder()` writes one, `clear_task_reminder()` deletes it so the task falls back to the global config value (returns whether anything was actually removed, so the caller can skip a redundant save).
- `sent`: Deduplication keys for reminder notifications (once the map exceeds 2000 entries, the 500 oldest are dropped).

All mutation methods acquire an `asyncio.Lock` and persist the full state via the save callback. Read methods return `deepcopy` of mutable state; `task_reminder_overrides()` additionally converts the string keys stored in KV back to `int` (skipping unparsable ones) so the scheduler can look tasks up directly.

### `tool_schema.py` — LLM tool docstring self-check

Stdlib-only validator for the `llm_tool` docstring constraint described above. `tool_schema_warnings(tool_name, docstring, parameter_names)` is a pure function over plain data (so both the plugin and the tests can feed it), and `schema_warnings_for_methods()` adapts a `{name: callable}` mapping via `inspect`. Rules: summary must be one line; every non-`event`/`self` parameter needs an `Args:` entry; entries need a type annotation; tools without parameters must not declare an `Args:` section.

The rules were calibrated against a known-good reference implementation (an 11-tool SSH plugin) to **zero false positives**, so a warning here means a real defect rather than style noise.

These rules are a *model* of the failure, not the failure itself. The authoritative counterpart is `parser_mismatch_warnings()`, which checks the parser's actual output against the signature. It takes the parse function as a **parameter**, so `main.py` injects the real `docstring_parser.parse` while the tests inject a stub — the logic is unit-tested without the dependency, and the plugin's `_check_with_docstring_parser()` runs it with the real parser on every startup (guarded by `try/except ImportError`, since a bare repo has neither `docstring_parser` nor `astrbot`). Two things to preserve if you touch it: it feeds the **raw `__doc__`**, not `inspect.getdoc()`, because that is what AstrBot passes; and it reports a parser exception rather than swallowing it, since a raising parser means the same total parameter loss.

Keep both layers — the rule-based one is a readable statement of the constraint, the parser-based one is the ground truth.

### `push_channels.py` — Pluggable reminder delivery

Stdlib-only, so it can be top-level imported by tests — which is why the actual `MessageChain` construction is **injected** as a `send_text(umo, text)` callable rather than imported. Contains the `PushChannel` protocol (`name`, `is_enabled()`, `async send(text) -> bool`), the concrete `AstrBotChannel`, `normalize_kinds`/`unknown_kinds`, `build_channels`, and `format_push_status`.

`AstrBotChannel.name` is the target `umo`; that is deliberate, because the dedup key `"{channel_umo}|{task_id}|{due_date}"` and the `_channel_failures` counters both predate this module and key off the same string. A trailing comment block documents the `CapsuleChannel` extension point and why it is not implemented yet: it is a network path nothing here can verify, and shipping an unverifiable send path would put a silent failure mode in the middle of the reminder pipeline.

### `_conf_schema.json` — Plugin configuration

Defines the WebUI configuration form: `vikunja_url`, `api_token`, `default_project`, `allowed_qq_sender_ids`, `timezone`, `reminder_minutes`, `poll_interval_seconds`, `idle_poll_interval_seconds`, `project_cache_ttl_seconds`, `request_timeout_seconds`, `max_list_items`, `push_channels`, `capsule_endpoint`, `capsule_token`. The last two are reserved extension points with no implementation behind them yet. Config is read through `self.config.get(..., default)` at each call site rather than into typed attributes, so the `_conf_schema.json` defaults are the fallback of record.

### Tests

Four test files in `tests/` using standard `unittest`:

- `test_domain.py` (`unittest.TestCase`): Tests for time parsing, repeat parsing, argument parsing (both `add` and `edit`), clear-word/tri-state parsing, secretary guard logic, project resolution, task filtering/sorting, sender whitelist, and `next_poll_delay` cadence — plus `SearchTests`, `ParseTaskIdsTests`, `SubtaskRelationTests`, the `Parse{Subtask,Bulk,Project,Move}ArgumentsTests`, the label suites (`ParseLabelChangesTests`, `MergeLabelChangesTests`, `ParseLabelArgumentsTests`, `LabelChangeFromSpecTests`, `LabelIndexTests`, `TaskLabelFilterTests`, `EditLabelFlagTests`), `RepeatRuleTests`, and `CompletedSinceTests`/`WeeklyReportTests`. `RepeatRuleTests` pins the refusal side, not just the happy path: that `每周` is *not* mistaken for a weekday rule, that `monthly` is *not* mistaken for a month-interval rule, and that the refusal names an executable alternative.
- `test_vikunja.py` (`unittest.IsolatedAsyncioTestCase`): URL normalization, plus `MergeUpdateTaskTests` — a `_RecordingClient` swaps the HTTP layer for a recorder so the assertions are on **the request body actually sent**, not on the intermediate dict. Its central assertions are that the body carries every `TASK_WRITABLE_FIELDS` key *and* the side-effect `xorm:"-"` fields (`reminders`/`is_favorite`/`labels`/`assignees`), while `TASK_ECHO_EXCLUSIONS` members stay out; together those are the regression line against someone reintroducing a partial write. `SAMPLE_TASK` deliberately contains both categories, so weakening either assertion is visible. `ProjectWriteTests` (same shape for `PROJECT_ECHO_FIELDS`, plus that a create is a `PUT /projects` carrying *only* a title) and `RelationTests` (the parent-in-URL/child-in-body direction) cover batch 2. The recorder exposes `bodies(method)` rather than only `posted_bodies()` — a create is a `PUT`, so a POST-only accessor unpacks to nothing. `LabelWriteTests`, `PaginationTests` and `CompletedSinceTests` cover batch 3; `_PagingClient` records the **raw params list** (not a dict) precisely so the "duplicate `sort_by` keys survive" assertion isn't self-defeating, and `param_count()` exists for that one check.
- `test_push_channels.py` (`unittest.TestCase`): `NormalizeKindsTests` (the `None` vs `[]` asymmetry), `AstrBotChannelTests` (that a `None` return counts as success), `BuildChannelsTests`, `FormatPushStatusTests`.
- `test_state_store.py` (`unittest.IsolatedAsyncioTestCase`): Async tests for channel registration, reminder thresholds, dedup marking, and persistence.
- `test_tool_schema.py` (`unittest.TestCase`): Both the validator's own rules and a real self-check of the seven plugin tools, by parsing `main.py` with `ast` — including the exact tool-name list, each tool's exact parameter list, and that every `vikunja_*` name mentioned in `SECRETARY_PROMPT` is actually registered.

Tests import modules directly (e.g., `from todo_domain import ...`) since the plugin is not installed as a pip package. **`main.py` is never imported by tests** — it needs `astrbot.api`. `test_tool_schema.py` reaches it through `ast` instead, which is why the "exactly these seven tools discovered" assertion matters: if the AST walk silently found nothing, the per-tool assertions would pass vacuously. Everything else in `main.py` (the plugin class, the loops, the send paths) is only exercised by running it under AstrBot.

## Key design decisions

- **"Rules + tool guards" pattern**: The secretary prompt gives the LLM rules, and `secretary_clarification_reason()` provides a second layer of enforcement in code — if the LLM still calls `vikunja_create_task` with incomplete info, the tool returns a clarification prompt instead of creating a bad task.
- **Edit, never delete-and-recreate**: prior to `vikunja_update_task` the only way to change a task's title or due date was to delete it and make a new one, which changes the task ID and breaks every reference to it (including the reminder dedup keys and any per-task threshold). Anything that modifies an existing task goes through `vikunja_update_task` / `/todo edit` → `_apply_edits`. `SECRETARY_PROMPT` rule 16 states this explicitly, because the model will otherwise take the recreate shortcut when a tool call fails.
- **One write path per kind of change, not one per entry point**: `_apply_edits()` takes a list of `EditSpec`s, so `/todo edit`, `/todo bulk`, and the LLM tool's `task_ids` all run the same code — including the parts that produce no visible output (resolving the project selector, persisting a per-task reminder threshold, waking the reminder loop). Batch adds per-task error isolation on top; it does not fork the path. The batch parsers likewise share one selector resolver, so a batch naming the same project three times resolves it once.
- **Refuse what the backend cannot express; never round it off.** Vikunja has no concept of "which weekday", so `每周一/三/五` is rejected with a named alternative (use `7d` if the due date already falls on that day, or create one task per weekday) instead of being mapped to a nearby interval. The same reasoning rejects `每 N 个月`. An approximation here is uniquely bad because it fails *quietly and later*: the task simply stops appearing on the expected day, weeks after the command that caused it, with nothing in the transcript to connect the two. `SECRETARY_PROMPT` rule 23 tells the model the same thing, because otherwise it will pick the closest-sounding rule on the user's behalf.
- **A statistic must be honest about its blind spots.** `/todo week` reports on `done_at` (a real indexed column, refreshed by the completion path) and not `updated` (refreshed by any edit). Zero-value `done_at` rows are dropped client-side, and the empty-window message says "no completed tasks in this window" rather than implying zero work was done — the known under-counting paths (created-as-done, kanban done-bucket, CSV import) are documented in the README instead of being papered over.
- **Labels are a separate route group, not a task field.** `POST /tasks/{id}` never carries labels; they go through `/tasks/{id}/labels` and `/labels/bulk`. Adding requires a label **ID** and errors if already attached, so the add path reads the task first even though it looks like it could skip the read.
- **Platform symmetry**: QQ and WeChat are treated identically for task operations; the only difference is QQ's optional sender ID whitelist.
- **Deep copying in StateStore**: Read methods return `deepcopy` of mutable state to prevent accidental mutation bypassing the save callback.
- **Vikunja time format**: Times are sent/received in UTC ISO 8601 with `Z` suffix (not `+00:00`). `from_vikunja_time` treats null and Vikunja's zero-value `0001-...` dates as "no due date".
- **Client-side sorting is authoritative**: `list_tasks()` passes `sort_by`/`order_by` to the API, but every displayed list is re-sorted in `select_tasks()` via `task_sort_key()` (priority desc, due asc, id asc; missing due dates sort last). Change the ordering in `todo_domain.py`, not in the API params.
- **Errors become chat text**: `VikunjaError` carries messages already phrased for the end user in Chinese, so callers display `str(exc)` rather than logging and re-wrapping.
